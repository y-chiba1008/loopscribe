# loopscribe 要件・設計資料(実装担当への引継ぎ)

- 作成日: 2026-11-02
- 状態: 要件確定・設計済み・**未実装**(モデル検証も未実施)
- 対象読者: 実装を担当するコーディングエージェント/開発者
- 関連: `README.md`、`AGENTS.md`、`scripts/bench_models.py`、`pyproject.toml`

---

## 1. 目的

PCで再生されている音声(システム音声)を、**ローカル(GPUなし・従量課金なし)で日本語に文字起こし**するCLIツールを作る。
リアルタイム性は重視しない。低スペックPCで安定して動くこと、長時間の音声を取りこぼさないことを優先する。

## 2. 前提・制約

| 項目 | 内容 |
|---|---|
| 実行OS | **Windowsのみ**(WASAPIループバック) |
| 開発環境 | WSL2(コア部分の開発・テスト)+ Windows実機(音声取得の確認) |
| Python | **3.13以降** |
| 想定PC | Core i5-8350U(4コア8スレッド)、RAM 8GB、GPUなし(Intel UHD 620) |
| 言語 | 日本語 |
| コスト | 従量課金なし。完全ローカル処理(通信はモデルのダウンロード時のみ) |
| 配布 | GitHubから `uv tool install git+https://...`(自分用。PyPI公開は未定) |
| モデル | Whisper `small`(faster-whisper形式)。モデル検証で確定(決定ログ#17)。`--model kotoba` で kotoba-whisper に切り替えられる(決定ログ#20) |
| コマンド名 | `loopscribe`(変更する場合は `pyproject.toml` の `name` と `[project.scripts]`、パッケージ名を変える) |

## 3. スコープ

**初期版に含む**

- システム音声の取得、文字起こし、コンソールとtxtへの出力
- 進捗のプログレスバー表示
- モデルのダウンロード用サブコマンド、デバイス一覧サブコマンド
- Ctrl+Cでの停止(バックログの処理を完了してから終了)

**初期版に含まない(将来拡張。§12)**

- マイク入力、音声ファイルの文字起こし
- SRT / JSONL などの出力形式、設定ファイル、推論パラメータのCLIオプション化
- バックログの破棄と欠落マーカー
- Windows以外のOS

## 4. 確定要件

### 機能要件

| ID | 要件 |
|---|---|
| FR-01 | 出力デバイスのWASAPIループバックで、システム音声を取得する(マイクは対象外) |
| FR-02 | 約30秒のチャンク(前後3秒の重なり)で逐次文字起こしする。VAD(無音スキップ)を使う |
| FR-03 | 結果をコンソールとtxtファイルの両方に、タイムスタンプ付きで出力する(UTF-8) |
| FR-04 | txtの保存先は `-o/--output-dir`(**既定: カレントディレクトリ**)。ファイル名は `loopscribe_YYYYMMDD_HHMMSS.txt` |
| FR-05 | `--device` で対象の出力デバイスを指定できる(番号、または名前の一部)。既定は既定の出力デバイス |
| FR-06 | `devices` サブコマンドで、対象にできる出力デバイスを一覧表示する |
| FR-07 | `download-model` サブコマンドでモデルを事前取得できる(`--model` で対象を選ぶ)。`start` 時に未取得なら自動で取得する |
| FR-08 | Ctrl+C 1回目で録音を停止し、未処理の音声を処理してから終了する。2回目で即時中断する |
| FR-09 | **文字起こしの遅れは無制限に許容する。未処理の音声は破棄しない**(メモリに保持する)。破棄マーカーは出さない |
| FR-10 | `処理済み時間 / 録音時間` をプログレスバーでリアルタイムに表示する |
| FR-11 | モデルに依存しない設定値(チャンク長など)は定数ファイル(`constants.py`)で定義する。CLIオプションにしない |
| FR-12 | `--model` で文字起こしのモデルを選べる(`small` / `kotoba`。既定は `small`)。推論パラメータはモデルごとに固定値を持ち、CLIオプションにしない(§6.8) |

### 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 | RAM 8GBの環境で、数時間の連続実行に耐える(バックログの保持量は§6.4で見積もり) |
| NFR-02 | **警告のみの方針**: 続行可能な問題は警告を出して継続する。起動時の致命的な状況は、エラーを出して終了する(§9) |
| NFR-03 | Windowsコンソールで日本語が文字化けしない(標準出力・ファイルともUTF-8) |
| NFR-04 | WSL(Linux)で `uv sync` とテストが通る(Windows専用の依存は環境マーカーで除外し、importも遅延する) |

## 5. CLI仕様

```
loopscribe start [--device DEVICE] [-o, --output-dir DIR] [--model {small,kotoba}]
loopscribe download-model [--model {small,kotoba}]
loopscribe devices
loopscribe --version
```

| コマンド | 内容 |
|---|---|
| `start` | 取得と文字起こしを開始する。モデル未取得なら先に自動取得する |
| `download-model` | `--model` のモデル(既定: `small`)を取得する(`faster_whisper.utils.download_model` を使用)。取得後に、モデルごとの設定の修正(§6.8)を行う |
| `devices` | WASAPIの出力デバイス(とループバック)の番号・名前・サンプルレート・チャンネル数を表示し、既定のデバイスを示す |

**終了コード**: 0=正常終了、1=エラー(起動時の致命的な状況など)、130=2回目のCtrl+Cによる中断。

**出力先の使い分け**: 本文・警告・プログレスバーは、すべて **richの単一のConsole** から出す(表示が崩れないように)。
標準出力がTTYでない(リダイレクトされている)場合は、プログレスバーを無効にして、本文だけを出す。

**本文の書式**(コンソールとtxtで共通)

```
[00:00:12] こんにちは、今日は…
[00:00:41] 次の話題ですが…
```

- 時刻は、録音開始からの経過時間 `[HH:MM:SS]`(セグメントの開始時刻)。時間は100以上になってもよい。
- txtの先頭に、ヘッダ行を1行入れる(例: `# loopscribe 開始: 2026-11-02 12:34:56 / モデル: ...`)。
- 1セグメントごとにflushする。

## 6. アーキテクチャ

### 6.1 全体像

```
AudioSource(差し替え可能) ──► convert ──► AudioBuffer ──► チャンク切り出し ──► Transcriber
 ├ WasapiLoopbackSource (Windows)  (mono/16k/int16)  (無制限に保持)                     │
 └ WavFileSource (開発・テスト)                                                         ▼
                                                    セグメントの担当割当て ──► Sink(コンソール / txt)
                                                                                      ▲
                                                                  ProgressReporter ◄──┘(処理済み/録音)
```

### 6.2 スレッド構成

| スレッド | 役割 |
|---|---|
| capture | `AudioSource` から読み、変換して `AudioBuffer` に追記する |
| transcribe | `AudioBuffer` からチャンクを切り出し、`Transcriber` で処理し、Sinkへ出力する |
| main | プログレスバーの更新と、シグナル待ち(`Event.wait(timeout)` を短い間隔で繰り返す) |

推論はネイティブコードの呼び出しで、その間はPythonのシグナル処理が遅れる。
メインスレッドで推論するとCtrl+Cが効くまでに時間がかかるため、**推論は必ず別スレッドで実行する**。
Windowsでは `Event.wait()` をタイムアウトなしで呼ぶとシグナルで中断できない場合があるため、短いタイムアウトを繰り返す。

停止の流れ:

1. Ctrl+C 1回目 → `stop_event` をセット → captureが終了(ストリームを閉じる)→ `AudioBuffer.close()` →
   transcribeが残りを処理(末尾の端数チャンクを含む)→ Sinkを閉じて終了。
2. Ctrl+C 2回目 → Sinkをflush → `os._exit(130)`(推論スレッドをデーモンにしても、終了処理でハングする恐れがあるため)。

### 6.3 モジュール構成(目標)

`AGENTS.md` のディレクトリ構成を参照。主なインターフェース:

- `AudioSource`(Protocol): `sample_rate`、`channels`、ブロックを順に返すイテレータ、`close()`。
- `Transcriber`(Protocol): `transcribe(samples_float32_16k) -> list[Segment]`。`Segment` は `start`/`end`(チャンク内の秒)と `text`、
  語の列 `words`(`Word` の `start`/`end`(チャンク内の秒)と `text`。担当割当て(§6.6)に使う)。
  実装はモデルごとに用意する(§6.8)。テスト用の偽実装も用意する。
- `ModelSpec`(抽象クラス): モデルごとの取得(`ensure` / `download`)、取得後の設定の修正(`fix_files`)、
  `Transcriber` の生成(`load`)。`models.MODELS` に名前で登録する。
- `AudioBuffer`: int16 / 16kHz / モノラルのサンプルを保持する。`append`、`total_samples`、`read(start, end)`、
  `trim_before(sample)`、`wait_for(n_samples, timeout)`、`close()`。スレッドセーフにする。
- `Sink`(Protocol): `write(segment_abs)`、`close()`。コンソール出力とtxt出力を実装する。

### 6.4 音声の取得と変換

- ループバック取得は `pyaudiowpatch`。既定の出力デバイスに対応するループバックデバイスを探して、コールバックで取得する。
  コールバックは軽く保ち(`queue.SimpleQueue` に積むだけ)、変換はcaptureスレッド側で行う。
- 変換: マルチチャンネル → モノラル(平均) → 16kHzにリサンプル → int16。
  リサンプルは、ブロックごとに `soxr.resample` を呼ぶと境界で不連続になるため、**ストリーム用の `soxr.ResampleStream`(状態を持つ)を使う**。
- `AudioBuffer` はint16 / 16kHz / モノラルで、**1秒あたり約32KB**(1時間で約115MB、8時間で約0.9GB)。
  推論に渡すときだけ float32 に変換する。この量なら、未処理の音声を破棄せずにメモリに保持しても、8GBのPCで問題にならない。
  処理済みの部分は、次のチャンクの重なり(3秒)を残して `trim_before` で解放する。
- **既知のリスク**: WASAPIのループバックは、再生が無音のときにデータが来ないデバイスがある。
  その場合、サンプル数ベースの経過時間は実時間より短くなり、タイムスタンプがずれる。
  初期版は「サンプル数ベースの経過時間」とし、Windows実機で挙動を確認する。
  ずれが問題なら、各コールバックの単調時計を見て、一定以上の空白に無音サンプルを挿入する案がある
  (VADが無音を飛ばすので、推論コストはほとんど増えない)。

### 6.5 チャンク処理

- チャンク長 L=30秒、重なり O=3秒、ステップ = L−O = 27秒。チャンクkは `[27k, 27k+30]` 秒。
- チャンクkは、録音が `27k+30` 秒に達した時点で処理を始める。録音の停止後は、まだカバーされていない末尾が
  `MIN_TAIL_SECONDS`(1秒)以上あれば、端数のチャンクとして処理する。
- Whisperのエンコーダは**常に30秒の窓**で処理するため、チャンクを30秒未満にしても1回あたりの計算量は減らない。
  30秒が、CPUでの効率が最も良い。
- 推論の呼び出し条件は、モデルごとの固定値(§6.8)。入力はfloat32 / 16kHz / モノラルのnumpy配列。
- `word_timestamps=True` は、どのモデルでも常に渡す(担当割当て(§6.6)に必須なので、切り替えない)。

### 6.6 セグメントの担当割当て(重複除去)

重なり部分の文が二重に出ないように、テキストの類似度ではなく、**語ごとの開始時刻で担当チャンクを決める**(決定ログ#19)。

- 語の絶対開始時刻 = チャンクの開始秒 + `word.start`。
- チャンクkの担当範囲は `[s_k + O/2, s_{k+1} + O/2)`
  (`s_k` はチャンクkの開始秒。先頭チャンクの下限は0、最終チャンクの上限は無限大)。
- チャンクkは、各セグメントのうち、絶対開始時刻が担当範囲に入る語だけを採用し、語の文字列をそのまま連結して strip したものを本文にする。
  本文が空なら出力しない。出力の時刻は、採用した最初の語の開始時刻(終了は、採用した最後の語の終了時刻)。
- 語が無いセグメントは、セグメントの絶対開始時刻(チャンクの開始秒 + `segment.start`)で判定し、セグメント全体を採用するか捨てる。
- 重なり区間の真ん中を境界にするので、各語は必ず1つのチャンクだけが採用する(重複も欠落も出ない)。
  境目をまたぐセグメントは、境界の前後で2つのチャンクに分かれて出力される。
  境界付近の語は、前後に十分な文脈があるチャンクのほうが採用される。
- 実装は `pipeline.owned_part`。

**セグメントの開始時刻で判定しない理由**(Issue #12): Whisperは、チャンクの最初のセグメントの開始時刻を、チャンクの先頭に寄せがちである。
新しい発話の大部分を含むセグメントが「前のチャンクの担当」と判定されて捨てられ、境目で発話が落ちる。

**救えない場合**: 重なり区間より前から始まり、担当チャンクの終端をまたぐ発話が、担当チャンクで出力されない場合は救えない
(検証では約10分の音声2本で1件ずつ。全体を1チャンクで処理した場合の取りこぼしと同程度)。
必要になったら、無音の位置でチャンクを切る案を別に検討する。

### 6.7 進捗表示

- `録音時間` = `AudioBuffer.total_samples / 16000`。`処理済み時間` = 完了したチャンクの終了位置(録音時間を上限とする)。
- 表示例: `処理済み 00:12:30 / 録音 00:15:00 ━━━━━━━╸━━ 83%  遅れ 00:02:30`
- 録音中は録音時間が増え続けるので、バーは100%にならない(最低でもチャンク1つ分は遅れる)。
  録音を止めると合計が固定され、バックログの処理が進むにつれて100%に近づく。
- 更新は、チャンク完了時と `UI_REFRESH_SECONDS` ごと(mainスレッドが共有カウンタを読む)。
- テキストの出力は `progress.console.print` などで、バーの上に流す(同じConsole経由)。
- **起動時のモデル読み込み**: 読み込みの間は「モデルを読み込み中」と表示する(richのスピナー。同じConsole経由)。
  対象PCでは、1回目の読み込みに約67秒(`small`)かかり、2回目以降は数秒だった(決定ログ#18)。
  モデルの読み込みが終わってから録音を始め、録音の開始をメッセージで知らせる(録音の開始時刻を、ユーザーが分かるようにする)。
  標準出力がTTYでない場合は、スピナーの代わりに1行のメッセージだけを出す。

### 6.8 モデルごとの推論(決定ログ#20)

モデルごとに `ModelSpec` を実装し、推論パラメータは各モデルのファイル(`models/<モデル>.py`)に固定値で置く。
チャンク処理(§6.5)と担当割当て(§6.6)は、どのモデルでも共通。違うのは、30秒チャンクの中の推論方法だけ。

| `--model` | 取得元 | 推論方法 | 固定のパラメータ |
|---|---|---|---|
| `small`(既定) | `small`(Systran/faster-whisper-small) | `WhisperModel.transcribe` で30秒チャンクをそのまま推論する | int8、`beam_size=1`、`vad_filter=True`、`condition_on_previous_text=False` |
| `kotoba` | `kotoba-tech/kotoba-whisper-v2.0-faster` | `BatchedInferencePipeline.transcribe` で、チャンク内をVADで無音の位置で区切り、15秒以下のクリップごとに推論する | int8、`beam_size=1`、`chunk_length=15`、`batch_size=1`、`without_timestamps=False`(時刻トークンあり) |

- kotoba-whisper は、固定長のウィンドウで発話の途中を切ると、その発話を飛ばしやすい。VADで区切ると発話の途中で切らないので、
  JSUTの検証で CER が small より約15〜25%低くなった(Issue #29)。`small` にこの方式を使うと大きく悪化するので、方式はモデルごとに分ける。
- **速度**: kotoba-whisper は開発機(Ryzen 5 3600、WSL2)で RTF 0.76〜1.00、対象PC(i5-8350U)では RTF 1.6〜2.2 以上で、遅れが累積する。
  対象PCでは `small` を使う。kotoba-whisper はRAMも多く使う(モデル約1.5GB)。

**kotoba-whisper の設定の修正(`alignment_heads`)**

- 語ごとの時刻(`word_timestamps=True`)は、ctranslate2 の `align()` で求める。デコーダーの特定の層とヘッドの cross-attention から、
  各トークンが音声のどの位置に当たるかを求める。使う層とヘッドの組は、モデルのフォルダの `config.json` の `alignment_heads` に書かれている。
- `kotoba-whisper-v2.0-faster` の `config.json` には、large-v3 の値(デコーダーの7〜25層)がそのまま入っている。
  kotoba-whisper のデコーダーは2層しかないので、存在しない層を参照してネイティブコードが異常終了する(終了コード139。Pythonの例外にならない)。
- `alignment_heads` を `[[1, h] for h in range(20)]`(最後の層の全ヘッド)に書き換える。
  ctranslate2 の変換ツールが、`alignment_heads` が無いときに使う既定値(デコーダーの後半の層の全ヘッド)と同じ。
- ctranslate2 は、モデルのフォルダの `config.json` を読む。外から値を渡すAPIは無い。メモリからファイルを渡す方法(`files=`)は、
  `model.bin`(約1.5GB)をメモリに読むのでRAMの使用量が倍になる。そのため、**Hugging Face のキャッシュの `config.json` をその場で置き換える**。
  - `snapshots/<リビジョン>/config.json` は、実体(`blobs/`)へのシンボリックリンク(Windowsでは通常のファイルのこともある)。
    修正した内容を一時ファイルに書き、`os.replace` でリンクごと置き換える。`blobs/` の実体には触らない。
  - huggingface_hub は、ファイルがあれば取り直さないので、修正は残る。
  - 確認と修正は、`download-model` の後と、`start` の起動時に毎回行う。値が違うときだけ書き換える
    (新しいリビジョンを取り直した場合や、別のツールで取得した場合にも直る)。

## 7. 定数(`constants.py`)

モデルに依存しない値だけを置く。推論パラメータは §6.8 のとおり、モデルごとのファイルに置く。

| 定数 | 暫定値 | 備考 |
|---|---|---|
| `CPU_THREADS` | `max(1, (os.cpu_count() or 2) // 2)` | 物理コア数の目安(論理コア数の半分)。対象PCで4、開発機で6。物理コア数のほうが論理コア数より速い(決定ログ#17、#20) |
| `LANGUAGE` | `"ja"` | |
| `SAMPLE_RATE` | 16000 | |
| `CHUNK_SECONDS` / `OVERLAP_SECONDS` | 30 / 3 | |
| `MIN_TAIL_SECONDS` | 1.0 | 停止時の端数チャンクを処理する最小の長さ |
| `LAG_WARN_SECONDS` | 600 | 遅れがこの値の倍数を超えるたびに、警告を1回出す |
| `BUFFER_WARN_MB` | 2048 | バッファがこの量を超えたら警告(破棄はしない) |
| `UI_REFRESH_SECONDS` / `SIGNAL_POLL_SECONDS` | 0.5 / 0.2 | |
| `OUTPUT_FILENAME_FORMAT` | `loopscribe_%Y%m%d_%H%M%S.txt` | |
| `OUTPUT_ENCODING` | `"utf-8"` | |

**ルール**: クラスや関数は、値を引数で受け取り、**引数の既定値として定数を使う**。
定数をグローバルに直接参照すると、テストでチャンク長や上限を変えられない(数秒のwavで境界処理を試すために必要)。

## 8. モデル検証(最初のタスク)

### 8.1 目的

CPU(i5-8350U / int8)で、kotoba-whisperが実用的な速度で動くかを確かめ、モデルと定数を確定する。

**注意(私の理解に基づく仮説。実測で確認すること)**: kotoba-whisperはlarge-v3系の蒸留モデルで、デコーダーは軽量化されているが、
エンコーダーはlarge-v3と同規模である。CPUではエンコーダーが支配的になりやすく、`small` より遅くなる可能性がある。

### 8.2 手順

1. `uv run scripts/prepare_bench_audio.py` で、ReazonSpeech の `tiny` から 1〜3分(既定120秒)の
   16bit PCM wav と正解テキストを `scripts/data/` に作る。生成物は gitignore し、リポジトリに含めない。
   事前にブラウザで [利用条件へ同意](https://huggingface.co/datasets/reazon-research/reazonspeech) する。
   未ログインなら、スクリプトがブラウザログインを始める。同意そのものはスクリプトに組み込まない。
2. 段階1: `uv run scripts/bench_models.py scripts/data/sample.wav --reference scripts/data/sample.txt`
   (既定のkotoba-whisperと`small`を比較)。
3. 段階2: 有力なモデルに絞り、`--beam-sizes 1 5 --threads 4 8 --vad on off` で条件を振る。
4. 結果(RTF・メモリ・CER)から、モデルと推論パラメータ(スレッド数、`beam_size` など)を決め、決定ログに追記する。

### 8.3 判断基準

遅れは無制限に許容する方針なので、**RTF>1でも即不採用にはしない**。ただし、遅れは累積する。

| RTF | 意味 |
|---|---|
| ≤ 0.7 | 余裕あり。遅れは増えない |
| 0.7〜1.0 | 可。遅れは増えない |
| > 1.0 | 遅れが累積する。録音T時間あたり、約 `T × (RTF − 1)` の遅れ(例: RTF 1.5で、1時間録音すると約30分遅れ) |

RTF>1のモデルを選ぶ場合は、想定する録音時間と、終了後にバックログを処理する待ち時間(`T × (RTF − 1)` 程度)を、ユーザーが許容できるかを確認する。
精度は、RTFとCERを並べて、速度と精度のトレードオフで判断する(閾値は、ユーザーが決める)。

### 8.4 注意

- 最初の1回はウォームアップとして捨てる(スクリプトが自動で行う)。
- 計測中は他の重い処理を止める。ノートPCは熱でクロックが下がりやすい。
- RSS(メモリ)はプロセス全体の概算。正確に比べるには、モデルごとに別プロセスで実行する。
- WSL2のCPU性能はネイティブに近いので、検証はWSLで行ってよい。WSL2のメモリ上限(既定は物理メモリの約半分)に注意する。

## 9. エラー処理(警告のみの方針)

| 状況 | 対応 |
|---|---|
| 起動時: 出力デバイスが見つからない | エラーメッセージ(`devices` で一覧を確認するよう案内)を出して終了(コード1) |
| 起動時: モデルが未取得で、取得にも失敗した | エラーメッセージを出して終了(コード1) |
| 実行中: 処理が追いつかず、遅れが増える | 警告のみ。`LAG_WARN_SECONDS` の倍数を超えるたびに、1回だけ表示する。音声は破棄しない |
| 実行中: バッファが `BUFFER_WARN_MB` を超えた | 警告のみ。破棄はしない |
| 実行中: 1チャンクの推論で例外が出た | 警告(該当区間の時刻を含める)を出し、そのチャンクをスキップして継続する。txtには何も書かない |
| 実行中: 取得ストリームの失敗・デバイスの切断 | 警告を出して録音を停止し、バックログを処理してから終了(コード1)。**確定** |

## 10. テスト・開発・配布

### テスト

- **サンプルwavでの文字起こしテスト**を軸にする。`WavFileSource` で、本番と同じ経路(変換 → バッファ → チャンク → 出力)を通す。
- 通常のテスト(高速)は、偽の `Transcriber` を使う。対象: チャンクの区間と境界、セグメントの担当割当て(重複・欠落なし)、
  出力の書式、進捗の計算、Ctrl+C相当の停止フロー。上限や長さは、数秒のwavで試せるように小さくして渡す。
- 実モデルのテストには `@pytest.mark.slow` を付ける(既定ではスキップ)。軽量なモデル(`tiny`など)か、
  検証で選んだモデルを使い、**完全一致ではなくCERで判定**する。
- テスト用のwavは数秒の短いものを `tests/data/` に置く。音声は、**著作権・プライバシーに問題のないもの**を、ユーザーが用意する。

### 開発と配布のフロー

1. WSL2(リポジトリは `~/` 配下)でコア部分を開発・テストする。`/mnt/c` 配下には置かない。
2. GitHubにpushし、Windows側で `uv tool install --reinstall git+https://github.com/<account>/loopscribe` を実行して実機で確認する。
3. モデルのキャッシュ(Hugging Face)はWSLとWindowsで別になる。ディスクの空きに注意する。
4. 開発中にWSLでパイプライン全体を手動で試すには、wavを流す開発用スクリプト `scripts/run_wav.py` を作る(CLIオプションにはしない)。

## 12. 将来拡張

- **マイク入力**: `AudioSource` を追加し、システム音声とミックスする(または別ストリームにする)。
- **出力形式**: SRT / JSONL など。セグメントは構造化データなので、Sinkの追加で対応できる。
- **音声ファイルの文字起こし**: `WavFileSource` を一般化する。
- **設定ファイル**: 定数の一部を外に出す。
- **モデルの追加**: `ModelSpec` を実装して `models.MODELS` に登録すれば、`--model` で選べる。
- **バックログの破棄を導入する場合**: 上限超過時に、最古の未処理チャンクを `GapMarker(start, end)` に置き換えてキューの順序を保ち、
  出力時に `[00:13:30-00:14:15 欠落: 45.0秒分を破棄]` のようなマーカーを本文に流す。欠落秒数は、残ったチャンクにカバーされていない区間
  (直前に残ったチャンクの終了位置から、次に残ったチャンクの開始位置まで)で計算し、欠落の前後では重複除去をしない。
  (初期版では実装しない。上記は検討済みの設計メモ)
- **他OS**: macOS / Linuxのループバック取得。
